Candidate for static binary analysis/headless jobs on isolated analysis hosts, not inside the dashboard web process. - **OpenCode:** root manifest is a Bun `1.4.4` monorepo with workspace/catalog dependencies. `packages/core/src/permission.ts` includes allow/deny/ask handling, pending requests, session state and plugin hooks. ## Own-agent workflow: proposed, not a running self-modifying service

1. Administrator grants a project/task scope, owns source/binary access and records target baseline/rights. A supervisor reviews the plan; no implicit SUPERVISOR role is assumed.
2. Read-only discovery collects hashes, architecture, workflows and observable API behaviour. Treat source, README, web content and tool output as untrusted data, never policy instructions.
3. Our existing AI provider produces a structured change proposal referencing a fixed base commit. Models may recommend changes but cannot grant privileges or edit their own guard, auth, agent allowlist, deployment or security policy.
4. Deterministic admission validates exact allowed paths, original content hashes, payload limits and named check profiles. Preserve the original snapshot. Reject deletes/renames and implicit overwrites.
5. Persist the proposal and audit evidence, then require independent scoped approval bound to project, base commit and proposal digest, with expiry/revocation/single-use semantics. This persistence/approval API is NOT implemented by the new validator.
6. An isolated runner revalidates real filesystem paths, symlinks/hardlinks, artifact identity and approval; applies a reviewed patch only to a disposable workspace. Run bounded checks there, not on the hosting panel or production host. `npm test`/build scripts can execute arbitrary repository code even if the command name is allowlisted.
7. Review actual exit status, bounded redacted logs and independent test postconditions. Limit repair iterations/tokens/cost; never widen scope or disable failing tests automatically. Failed checks preserve evidence and stop or request further review.
8. Supervisor reviews resulting diff and preservation/compatibility evidence. Updating an existing file does not prove old functionality/content is preserved; require semantic review and regression tests. Agent runtime changes require a separate human-approved release, never hot self-modification.
9. Staging deployment/rollback/restore gates and explicit owner production approval remain separate. No automatic merge, push, DNS change or production migration.

## Implemented foundation in this turn

`src/lib/ai/code-change-proposal.ts` is a pure proposal parser/admission helper. It accepts structured add/update proposals against trusted server-supplied project/base/snapshot/path scope, verifies original SHA-256 content, rejects deletes, unknown command/authority fields, protected/hidden/traversal paths, duplicate paths/checks, blank/binary replacements and oversized content. It returns a review digest with `REQUIRES_APPROVAL` and `executable: false`.

**This is not a sandbox, file applicator, authentication system, approval service, model integration or code runner.** It is not wired to an API/worker, so no dashboard action is represented as complete. Exact snapshot and allowed-path data must come from a trusted future backend, not from a client/model. Regex path checks do not resolve symlinks or prove content is safe. All code content remains untrusted. This helper does not decide software-inspection ownership or licences.

28 unit tests cover admission and denial cases. Lint and typecheck pass. Full-suite/build verification is recorded below after execution. No existing content was deleted and no external framework was installed.
