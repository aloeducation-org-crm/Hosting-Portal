# ALO commercial hosting: implementation evidence, 2026-11-18

**Review boundary:** source, scratch files/databases, real public GitHub reads, and disposable loopback application processes. No production node, customer DB, DNS zone, payment gateway or cloud resource was modified. The active branch is based on `bcaf73679214a24bd91d244c31191ae298811912`. This change is the first customer hosting path, not completion of the commercial hosting platform.

## Baseline and infrastructure access

The repository has a working Next.js control plane, signed/allowlisted node-agent operations, durable jobs, Git deployments, entitlement controls, and provider, DNS, backup and inventory surfaces. Review covered the active workflows, helpers, schema/deployment tooling, provider implementations, deployment and billing boundaries, and the existing office/Hostinger/Cloudflare runbooks. The current GitHub environment list showed only `production`; runner inventory returned HTTP 403. The sandbox had no container daemon or service DB daemon. No approved office/Hostinger staging login, delegated content zone, or usable provider/DB/backup access was available for a live infrastructure audit. Historical inventory and screenshots are not current measurements. Prefer reusing an audited, staging-isolated ALO node if available and within quota; no provider selection or allocation was made on the strength of a runbook or DB row.

Baseline: 1,370 passing tests, 1 skipped; repo audit 18/18. Existing risk areas outside this change include legacy deploy admission and local-build fallback, unverified runtime/proxy/TLS integration, and a legacy restore route that calls a live helper synchronously. It was not invoked. The new path never uses these helpers or calls hosts other than the approved ingress (if set), local edge and public GitHub.

## Reproducible evidence

- `npm run db:generate`, `npm run typecheck`, `npm run lint`, `npm test` (90 files, 1,384 passed, 2 skipped), `npm run build`, and `npm run build:worker` passed. The two skips were the external GitHub fixture by default and the existing build-isolation environment skip. The GitHub fixture was run separately. Repo audit passed 18/18; full-history merge audit covered 57 merges with no unexplained missing files. Final npm audits with and without dev dependencies reported 0 advisories; the first baseline install had reported 16 dev advisories, not reproduced by the later audit. No broad dependency upgrades were used to suppress them.
- The new migration was applied and reapplied by the real schema applier on a scratch copy, then passed `--verify` and `PRAGMA integrity_check`. All 496 existing rows across 127 tables matched the pre-migration copy exactly. Schema parity was checked on a migrated copy. The `db/custom.db` Git blob remained `1d0c3b01aeb898b2f207cc8b2f68e3214d5513ee`.
- Standalone smoke used the actual login/session cookie, CSRF gate, customer and operator routes, separate bundled worker and copied standalone edge. It used a schema-only scratch DB, ephemeral accounts, free test plan with a 1-site limit, and no external provider secrets. The second customer could not see/withdraw the site and could not deploy without a plan. Replaying the same request produced one reservation and one consent audit event. After a real public GitHub read, the separate edge served the pinned bytes; the API withheld a public URL. Withdrawal then returned origin 404 while preserving the bytes, returned the slot to the plan and created no orders or invoices.
- Standalone smoke sample: repo `octocat/Spoon-Knife`; commit `d0dd1f61b33d64e29d8bc1372a94ef6a2fee76a9`; two files; homepage SHA-256 `2b3919976ed3c3d176da250161d0d1c71052d518c4e56d63bcc57343e0e754e9`; publication job `c947bf62-36eb-4f1b-a7bd-4f1d2b8e3eae`, withdrawal job `ba2cb26a-0992-41f7-81e5-3c816b71706d`. These are disposable records, not a deployed customer or public URL.
- The two-process claim test had two separate Node workers contend for one site's lock. Only one claimed a job. Its process exited; expiry was advanced in the scratch DB, and a new worker finished the persisted deployment request. A separate failure-injection test demonstrated that a failed origin activation was moved out of routing, after which the same bytes were activated on retry without re-reading GitHub. DNS mismatch, body mismatch, TLS transport failure, and stale/moved-ingress evidence were **test boundary simulations**, not public DNS or trusted TLS acceptance.
- Optional GitHub-to-origin burst: 500 simultaneous loopback requests, 500 HTTP 200 responses with matching content (this run's p95 1,085 ms, p99 1,091 ms). This was one small cached-by-OS workload in one sandbox, no TLS, WAN, customer control traffic or billing/DB load. **It is not a 500-customer capacity result.** `systemd-analyze verify` passed on temporary copies with the local Node path substituted; systemd confinement and Nginx configuration have not been exercised on an approved host.
