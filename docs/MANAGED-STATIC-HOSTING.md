# Managed static hosting: staging pilot

**Status: IMPLEMENTED, NOT LIVE-VERIFIED.** This is an opt-in, build-free static site path. It has run against GitHub and a real loopback panel, worker and origin on a disposable database. It has **not** been enabled on an ALO hosting node, and no public DNS/TLS, production deployment, or payment was attempted. See [acceptance evidence and remaining product gates](audit/MANAGED-STATIC-HOSTING-EVIDENCE-2026-11-18.md).

## Customer and operator paths

- A verified customer with `WEBSITE_CREATE` and `WEBSITE_DEPLOY` opens **Deployments → Managed static hosting** (`/deployments/static`). Enter a public GitHub owner/repository, optional branch, and a label in the configured content zone. Select the existing active plan and confirm authorization to publish the files. There is no purchase, checkout, plan change, or new charge in this flow.
- `POST /api/deploy/static` records an audit entry and reserves a site slot in one DB transaction. `202` means **request recorded**, not running or live. The dedicated automation worker links an idempotent job, rechecks permission and entitlement and pins the GitHub commit and tree. Customers can inspect the release, job stages, origin check and separately observed public status.
- `/automation/static-hosting` shows the 100 newest requests for verified admins. Customers can only see their own records and cannot submit generic worker commands. The legacy HTTP and cron ticks are not permitted to run these jobs.
- **Recheck HTTPS** queues an owner-scoped run. A public link requires fresh matching evidence: the A answers must all equal the operator's approved IPv4, no AAAA answer, a trusted certificate for the managed hostname, and HTTP 200 with the expected release marker and homepage digest. A separate origin success does not imply any of those. Rechecks do not change DNS or issue a certificate. An observation is not an uptime guarantee. A changed ingress IP, failed recheck, pending withdrawal or evidence older than one hour suppresses the verified link on the next status refresh.
- **Withdraw website** requires typing the exact hostname. It queues a same-site job to move the release out of the routing tree and to confirm origin HTTP 404. It does not delete data, recycle the hostname, purge outside caches, change DNS, or change billing. It releases the plan slot only after the origin check. The bytes remain in `.held-<site-id>`. This is not an offsite backup. A withdrawn site's original job and audit history remain visible.

This path accepts a nonempty root `index.html` and a small allowlist of regular, nonexecutable HTML, CSS, JS, text, image and font files: 40 files, 2 MiB per file, 8 MiB total. It does not check out or run tenant code, install packages, or publish configuration or dotfiles. It rejects build manifests, submodules and Git LFS. Review the approved repository contents for secrets and authorization before posting them publicly. Private repos, uploads, arbitrary/customer domains, build steps, updates to an existing hostname, SPA rewrites, continuous monitoring, billing suspension/restoration and backup/restore are not part of this pilot. An expired plan blocks new publication and checks; it does not de-route an already published site. Operators should only enroll approved staging accounts and repos.

## Admission and capacity bounds

The plan site count includes active legacy website rows and nonwithdrawn static reservations. A failed reservation still counts until withdrawn. The installation cap (`STATIC_HOSTING_MAX_RESERVATIONS`, default 25) includes withdrawn and retained releases; this limits disk and queue growth without deleting customer data. Only increase it after a capacity and retention review. The worker checks free disk and stages on the release filesystem; replay accepts only the same site and pinned release. An origin verification failure moves that release out of the serving tree for bounded retry. Never delete an unknown directory to fix a stalled job.

GitHub reads use its public, unauthenticated API and no installation secret. API rate limits are real (one source fetch per asset plus metadata); don't onboard a burst of repositories or promise deploy throughput. Retry only after the applicable limit resets. Read-only asset serving at the edge and GitHub deployment throughput are different bottlenecks.

## Staging installation (operator with explicit approval only)

1. **Audit the existing node before choosing placement or spending.** Check authorized inventory, health and cgroup headroom, disk and backup availability, ports/firewall/NAT, trusted resolver and `api.github.com` egress, runner version, and actual certificate renewal path. Use an approved disposable DB and a dedicated volume. Confirm that no Website, Site, GitProject, proxy vhost, admin endpoint, or customer other than this pilot uses the content zone. Do not point customer-controlled content at the panel's registrable domain, or at an existing shared site. Don't change a running zone in place: drain/withdraw and verify served hostnames before rotating it.
2. Build the panel and bundles with `npm run build && npm run build:worker`. Test the additive migration `20261118120000_static_hosting` on an explicit **staging** database with the normal schema applier, then `--verify`. Do not run `db push`, reseed, or use a production DB to rehearse. This migration neither rewrites nor deletes existing rows. The bundled worker and panel must both be on the matching schema; keep feature variables unset until this is true.
3. Create a no-login `alo-static-edge` system user and group and a dedicated `alo-static-content` group on the approved host. The edge must not share the panel UID. For the shipped `alo-automation-worker.service` (UID `alo-panel`), provision a real, nonsymlink directory `/var/lib/alo-static/releases`, owned by `alo-panel:alo-static-content` and mode `2750`, on the approved volume. The parent must be traversable by both services; the edge gets read-only group access. Keep the directory writable by the automation worker only; do not expose it to customers via FTP, file manager, Docker mounts, or user processes. Validate the worker `ReadWritePaths` when using systemd and check effective permissions. A PM2 profile does not impose the systemd filesystem sandbox.
4. Install **only** the root-owned `.next/standalone/static-edge.cjs` bundle into `/usr/local/lib/alo-static-edge/`; do not copy the panel's `.env`, the panel bundle, or its DB to that service directory. Use `deploy/systemd/alo-static-edge.service` with an edge-only `/etc/alo-hosting/static-edge.env` (root-owned mode `0600`):

   ```dotenv
   STATIC_HOSTING_DOMAIN=sites.example.net
   STATIC_HOSTING_ROOT=/var/lib/alo-static/releases
   STATIC_HOSTING_EDGE_PORT=3187
   ```

   Use the actual approved zone in place of `sites.example.net`. Verify Node ≥22 at the unit's `ExecStart` path. Review the unit's filesystem and loopback restrictions (`IPAddressDeny` requires host support). Install/start only on the approved staging node; confirm the edge is bound to `127.0.0.1` and a foreign Host returns 404. The separate bundle is not installed or started by normal panel releases; update/restart it explicitly with matching builds.
5. For a public staging test, provision the approved wildcard DNS A record to the approved routable IPv4, with no AAAA, and an independently valid wildcard certificate covering exactly one label. Obtain and renew it with an approved operator-controlled DNS validation process; this change does not call a DNS or certificate API. Configure the staging-only [Nginx example](../deploy/nginx/managed-static.conf.example) at the public ingress. Ensure Host and SNI route to that content vhost, not to the panel, and don't enable CDN caching or body transformations. Strip cookies and auth at the proxy. Validate the config (`nginx -t`), certificate chain, actual proxy behavior and firewall before enabling the listener. The published example assumes direct IPv4 ingress, not an orange-cloud/proxied zone or dual stack. If using multi-hop routing, first verify the approved address and source-IP rate limit behavior on staging.
6. In the **staging** panel and automation worker env, set the same zone, port and release directory, the tiny reviewed reservation limit, and `STATIC_HOSTING_PUBLIC_IPV4` only when the real approved ingress is reachable. Set the actual panel `APP_URL` and `NEXTAUTH_URL`; same registrable domains are rejected. `DEPLOY_INLINE_WORKER=false` keeps the existing deploy execution out of the panel; the static handler always runs only from the standalone automation tick. Clear the setting and roll back ingress with the operator if setup fails; **unsetting panel config alone does not stop the edge from serving on a previously exposed ingress**.

## Rehearsal and release gates

The disposable sandbox smoke requires a standalone build and outbound public GitHub access. It does not need a host, DNS account, private GitHub access or payment credentials:

```bash
npm run build && npm run build:worker
node scripts/smoke-static-hosting.mjs octocat/Spoon-Knife
# Optional parallel origin-only burst and GitHub transport verification:
LIVE_STATIC_FIXTURE_REPO=octocat/Spoon-Knife npx vitest run tests/static-hosting.test.ts -t 'reads real public GitHub'
```

Where egress is mediated by a trusted local proxy, give Node the approved system CA bundle using `NODE_EXTRA_CA_CERTS`; never disable certificate verification. The smoke creates its own accounts, DB and content on loopback, with no access to a deployed DB. Both the optional burst and the standalone smoke skip public ingress, by design.

On approved staging, repeat the customer flow in a browser using a verified test customer, a subscribed plan and a reviewed repo. Save evidence of CSRF/auth isolation, request ID, job ID, commit SHA, origin time and release digest. From **outside the staging node**, resolve both A and AAAA and check the real URL and `/.well-known/alo-static-release` over trusted HTTPS (no `-k`). Compare both digests with the panel report. Run second-tenant and over-quota checks, stop a staging worker holding a lease, restart and verify one publication, then withdraw the pilot site and check 404 and retained bytes. Audit quota, disk use and job depth. Treat a failed check as a blocker; do not mark the pilot `VERIFIED COMPLETE` or promote to production before independent public checks and operator approval.
